# pager-lang v0.2.0 — Core

**The first release with domain logic.** v0.2.0 turns the v0.1.0 scaffold into a working memory layer: it maps page-aligned regions of virtual memory, changes their access permissions on demand, optionally flanks them with guard pages, and frees them on drop. The release introduces the whole public surface — the `Region` type, the `Protection` enum, the `PagerError` type, and the `page_size` query — together with full rustdoc, an `API.md` reference, property tests, and Criterion benchmarks. The surface remains pre-1.0 and will be frozen at `1.0.0`.

## What is pager-lang?

The memory foundation a JIT needs. A just-in-time compiler emits machine code at run time and then jumps into it, which requires memory the operating system will let the CPU *execute* — something ordinary heap allocations are not. pager-lang hands out that memory: page-aligned regions whose access permissions (read, write, execute) can be changed independently of the rest of the address space, with optional guard pages, and nothing more. Regions are backed by `mmap` on Unix and `VirtualAlloc` on Windows through direct FFI, with no third-party dependencies on the core path.

## What's new in 0.2.0

### The `Region` type

`Region` is the type the crate is built around: an owned block of page-aligned virtual memory that frees itself when dropped. It is created read/write, so code or data can be written in, then moved to another protection — usually read+execute — to be run.

```rust
use pager_lang::{Protection, Region};

let mut region = Region::new(4096).expect("map a page");
region.write(0, &[0x90, 0x90, 0xC3]).expect("write while writable");
region.protect(Protection::ReadExecute).expect("flip to executable");
assert_eq!(region.protection(), Protection::ReadExecute);
```

The requested length is rounded up to a whole number of pages, so `len()` is the real, page-aligned size and is at least what was asked for. `Region` is `Send`, `Sync`, and `Debug`.

### Write xor execute, enforced by the type

The intended flow is *write xor execute* (W^X): fill the region while it is writable, then flip it to read+execute before running it, so the same page is never writable and runnable at once. The safe accessors enforce the discipline — `as_mut_slice` returns `None` unless the region is writable, `as_slice` returns `None` unless it is readable — so a safe call can never hand out a slice that would fault.

```rust
use pager_lang::{Protection, Region};

let mut region = Region::new(32).expect("map");
assert!(region.as_mut_slice().is_some());     // writable now

region.protect(Protection::ReadExecute).expect("flip");
assert!(region.as_mut_slice().is_none());     // no longer writable
assert!(region.as_slice().is_some());          // still readable
```

`write` is the bounds-checked path for loading code: it rejects a write past the end with `PagerError::OutOfBounds` and a write to a non-writable region with `PagerError::NotWritable`, rather than faulting.

### Guard pages

`Region::with_guard_pages` flanks the usable region with inaccessible pages, so a read or write that runs off either end faults immediately instead of silently corrupting whatever is mapped next — cheap insurance for a code buffer a compiler is filling. On Unix the guards are `PROT_NONE` pages; on Windows they are reserved-but-uncommitted pages, which fault on access at no commit-charge cost.

```rust
use pager_lang::Region;

let region = Region::with_guard_pages(1024).expect("map guarded");
assert!(region.has_guard_pages());
```

### Executing generated code

The safe surface gets the memory into the right state; the final transmute-and-call is the caller's `unsafe` step. On x86-64 it is direct:

```rust
# #[cfg(target_arch = "x86_64")]
# {
use pager_lang::{Protection, Region};

// mov eax, 42 ; ret
const CODE: [u8; 6] = [0xB8, 0x2A, 0x00, 0x00, 0x00, 0xC3];
let mut region = Region::new(CODE.len()).unwrap();
region.write(0, &CODE).unwrap();
region.protect(Protection::ReadExecute).unwrap();

// SAFETY: a valid no-argument x86-64 function returning in rax, in read+execute memory.
let f: extern "C" fn() -> u64 = unsafe { core::mem::transmute(region.as_ptr()) };
assert_eq!(f(), 42);
# }
```

On architectures with separate instruction and data caches (AArch64, for instance) the caller must also synchronize the instruction cache before running freshly written code; on x86 and x86-64 this is automatic. A complete runnable example is in `examples/jit_function.rs`.

### Errors that carry the OS code

Every fallible operation returns `Result<_, PagerError>`; the crate never panics on a recoverable condition. The OS-level variants (`Map`, `Protect`) carry the raw error code — `errno` on Unix, `GetLastError` on Windows — so the underlying cause is not lost. `PagerError` is `#[non_exhaustive]` and implements `Display` and `std::error::Error`.

### `no_std` and `serde`

The crate is `#![no_std]`-capable: with `default-features = false` it needs only `core` and reaches the operating system through FFI exactly as it does with `std`. The optional `serde` feature derives `Serialize` / `Deserialize` for the `Protection` and `PagerError` value types (a live `Region` is an OS resource, not a value, and is not serializable).

### Tests and benchmarks

The lifecycle is exercised end to end. Integration tests map, write, protect, and free regions; the x86-64 tests assemble a function, flip the region to executable, and run it through a transmuted function pointer on both the System V and Windows x64 calling conventions. Property tests check the size, bounds, and protection invariants across a wide range of inputs. Criterion benchmarks cover mapping, protection changes, and writes; mapping and protection costs are dominated by the kernel transition and are essentially independent of region size (for example, mapping and freeing a region is roughly 1.0 µs, a guarded one roughly 2.2 µs, and a read/write → read/execute → read/write protection cycle roughly 0.32 µs on the reference machine).

## Breaking changes

**None.**

v0.1.0 had no domain logic, so the entire public surface is new and additive. The crate's internal `#![forbid(unsafe_code)]` was replaced with scoped, documented `unsafe` — required to call the OS memory APIs — but this is not a visible API change.

```bash

cargo test
```

All green on both Linux and Windows, including the x86-64 tests that assemble and execute real machine code on each platform. Test counts at this tag:
